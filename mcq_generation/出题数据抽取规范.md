### 2.3 表关联键

```text
admissions.subject_id ──→ patients.subject_id          (1:1)
admissions.hadm_id ────→ diagnoses_icd.hadm_id          (1:N)
                      ──→ procedures_icd.hadm_id         (1:N)
                      ──→ poe.hadm_id                    (1:N)
                      ──→ labevents.hadm_id              (1:N)
                      ──→ prescriptions.hadm_id          (1:N)
                      ──→ services.hadm_id               (1:N)
                      ──→ discharge.hadm_id              (1:N)
                      ──→ radiology.hadm_id              (1:N)
                      ──→ edstays.hadm_id                (1:1 或 0)

edstays.stay_id ──────→ triage.stay_id                  (1:1)
                    ──→ vitalsign.stay_id                (1:N)

poe.poe_id + poe_seq ─→ poe_detail.poe_id + poe_seq    (1:N)
labevents.itemid ────→ d_labitems.itemid               (N:1)
```

**关联约束**: 每条住院级源记录的 `subject_id` 必须与 `admissions.subject_id` 一致。冲突时视为全局数据完整性错误，终止抽取。

## 三、抽取管线架构

### 3.1 管线总览

```text
Stage 0  加载 admissions → 候选 Visit 集合
Stage 1  关联 patients → 人口统计筛选（年龄>=18、性别有效）
Stage 2  关联 diagnoses_icd + d_icd_diagnoses → 诊断筛选（有效主诊断）
Stage 3  关联 discharge(DS) → 出院小结筛选（有效 DS + Chief Complaint）
         ──── 纳入漏斗结束，得到 eligible Visit 集合 ────
Stage 4  提取 DS 章节字段（8 个 narrative + 4 个 disposition 章节 + 全文）
Stage 5  提取结构化临床字段（investigations/diagnoses/treatments）
Stage 6  提取科室/去向/生命体征字段
Stage 7  组装 + 验证 + 写入 JSONL
```

### 3.2 漏斗模型

```
admissions 全部住院          N0
  - 无有效 patients 关联
  - 年龄 < 18 或无法计算
  - 性别无效
                              ↓ Stage 1
人口统计通过                  N1
  - 无有效 seq_num=1 主诊断
  - 主诊断无法连接字典
                              ↓ Stage 2
诊断通过                      N2
  - 无 note_type=DS 的出院小结
  - DS 无明确 Chief Complaint
                              ↓ Stage 3
eligible Visit                N3
```

**Stage 3 之后不再排除 Visit**。对 eligible Visit 中的非必需字段，缺失按规则表示，不影响 Visit 纳入。

### 3.3 处理顺序

- Stage 0-3 顺序执行，每个 Stage 的输出约束下一个 Stage 的输入范围。
- Stage 4-6 可以并行（均只处理 eligible Visit 的 `hadm_id`），但同一 `hadm_id` 的各阶段结果在 Stage 7 汇合。
- 所有源表按 `hadm_id` 过滤后再处理；`hadm_id` 为空或不在 admissions 中的记录直接忽略。

## 四、Visit 定义与纳入条件

### 4.1 Visit 定义

- 一个 Visit 等于一个 `hadm_id`，是行的唯一主键。
- `hadm_id` 来自 `admissions.csv`，不得从其他表推导或改写。
- 每个 `hadm_id` 在 admissions 中唯一非空；重复或缺失视为全局错误，终止抽取。
- 同一 `subject_id` 可对应多个 `hadm_id`；各 Visit 独立处理，不跨住院合并。

### 4.2 Stage 0: 候选 Visit

- 从 `admissions.csv` 读取全部行。
- `subject_id` 和 `hadm_id` 去首尾空白，空值视为全局错误。
- `hadm_id` 重复视为全局错误。
- 保留 admissions 源文件顺序作为候选顺序。
- 可选 `--limit N` 截取前 N 个候选。

### 4.3 Stage 1: 人口统计筛选

**关联**: `admissions.subject_id` -> `patients.subject_id`（必须 1:1）。

**计算**:

```text
age_at_encounter = anchor_age + year(admittime) - anchor_year
```

**排除条件**（任一满足即排除）:
- `patients` 关联缺失、重复或 `subject_id` 冲突
- `anchor_age`、`anchor_year` 或 `admittime` 无效
- `age_at_encounter` < 18
- `gender` 不是 `M` 或 `F`

**同时提取的字段**: `demographics.age_at_encounter`(#3)、`demographics.sex`(#4)。

### 4.4 Stage 2: 诊断筛选

**关联**: `admissions.hadm_id` -> `diagnoses_icd.hadm_id`。

**主诊断有效条件**:
- 当前 Visit 恰好存在一条 `seq_num=1` 记录
- `icd_code` 去首尾空白后非空
- `icd_version` 为 9 或 10
- `icd_code + icd_version` 能精确连接 `d_icd_diagnoses` 到唯一非空 `long_title`

**排除条件**: 无有效主诊断、有多条 `seq_num=1` 记录、或主诊断无法连接字典。

**同时提取的字段**: `diagnoses.primary`(#23-#25)、`diagnoses.other`(#26)。

### 4.5 Stage 3: 出院小结筛选

**关联**: `admissions.hadm_id` -> `discharge.hadm_id`（`note_type=DS`）。

**DS 候选条件**:
- `note_type = DS`（`AD` 补充记录不纳入）
- `hadm_id` 等于当前 Visit
- `subject_id` 与 admissions 一致
- `text` 非空

**DS 选择规则**: 对每份候选 DS 独立解析 Chief Complaint 章节。只保留包含明确非空主诉的候选。在有效候选中按以下优先级降序选最新:

1. `note_seq`（越大越新）
2. `charttime`（越大越新）
3. `storetime`（越大越新；空值排在非空之后）
4. `note_id`（字符串降序）

**排除条件**: 无符合条件的 DS，或所有候选 DS 均无明确非空 Chief Complaint。

## 五、逐阶段提取规则

### 5.1 Stage 4: DS 章节字段

选定的 DS 同时作为以下 13 个字段的共同来源，不合并不同 DS 的章节:

`narrative.chief_complaint`(#15)、`narrative.history_of_present_illness`(#16)、`narrative.past_medical_history`(#17)、`narrative.social_history`(#18)、`narrative.medications_on_admission`(#19)、`narrative.allergies`(#20)、`narrative.physical_exam`(#21)、`disposition.brief_hospital_course`(#33)、`disposition.discharge_medications`(#34)、`disposition.discharge_condition`(#35)、`disposition.discharge_record`(#36)、`narrative.discharge_note_full`(#37)。

#### 已知顶层标题列表

```text

Brief Hospital Course

Discharge Medications

```

#### 章节解析算法

1. 将 `text` 中的 `\r\n` 和 `\r` 统一为 `\n`
2. 用正则匹配顶层标题行：行首可选空白 + 标题文本（忽略大小写）+ 可选冒号 + 行尾
3. 对每个目标章节，内容从标题行之后开始，到下一个已知顶层标题行之前结束
4. 去除章节内容首尾空白
5. 章节内容为空时，对应字段写 null（chief_complaint 为空时排除 Visit）

#### 逐章节字段

| # | 字段路径 | 匹配标题 |
|--:|---|---|
| 15 | narrative.chief_complaint | Chief Complaint |
| 16 | narrative.history_of_present_illness | History of Present Illness |
| 17 | narrative.past_medical_history | Past Medical History |
| 18 | narrative.social_history | Social History |
| 19 | narrative.medications_on_admission | Medications on Admission |
| 20 | narrative.allergies | Allergies |
| 21 | narrative.physical_exam | Physical Exam |
| 33 | disposition.brief_hospital_course | Brief Hospital Course |
| 34 | disposition.discharge_medications | Discharge Medications |
| 35 | disposition.discharge_condition | Discharge Condition |
| 36 | disposition.discharge_record | Discharge Instructions |
| 37 | narrative.discharge_note_full | （不截取章节，保存 text 全文） |

**discharge_record(#36) 特殊规则**: 匹配 `Discharge Instructions`（不是 Follow-up Instructions）。原因见字段规范 §6.7。

**follow-up instructions 不可用性检测**: 抽取时对选定 DS 检测 Follow-up Instructions 章节内容。如果去除空白后内容仅为 `___` 模式，记录警告日志（不阻断抽取），确认该字段确实不可用。

### 5.2 Stage 5: 结构化临床字段

#### investigations（#22）

单一字段，包含住院期间全部检查检验。分为 laboratory / radiology / cardiology / respiratory 四个子数组。

**Laboratory 子数组**（来源: `labevents` + `d_labitems`）:
- 关联: `hadm_id` 匹配，`labevents.itemid` -> `d_labitems.itemid`
- 有效结果: `value`、`valuenum` 或 `comments` 至少一个非空
- 聚合: 按 `itemid` 分组，同项目的全部有效结果归入 `results` 数组（按 charttime 升序，时间相同时用 storetime/labevent_id 排序）
- 保存: `{itemid, label, fluid, category, results: [{charttime, value, valuenum, valueuom, ref_range_lower, ref_range_upper, flag, comments}]}`

**Radiology 子数组**（来源: `radiology` + `radiology_detail`）:
- 关联: `hadm_id` 匹配，`radiology.note_id` -> `radiology_detail.note_id`
- 正式报告: 只使用 `note_type = RR`
- 项目识别: `radiology_detail` 中 `field_name = exam_name` 对应的 `field_value`
- 项目选择: 同一 `exam_name` 只保留 `charttime` 最早的报告
- 保存: `{exam_name, charttime, text, details: [{field_name, field_value, field_ordinal}]}`

**Cardiology / Respiratory 子数组**（来源: `poe` + `poe_detail`）:
- 过滤: `transaction_type='New'`，`order_type IN ('Cardiology', 'Respiratory')`
- 明细关联: `poe_detail` 通过 `poe_id + poe_seq` 连接 `poe`
- 保存: `{order_subtype, ordertime, poe_detail: [{field_name, field_value}]}`
- 去重: 同一 `order_type + order_subtype + 排序后 poe_detail 内容` 相同的只保留最早一条

**输出**: JSON 对象 `{laboratory: [...], radiology: [...], cardiology: [...], respiratory: [...]}`。

#### diagnoses（#23-#26）

（Stage 2 已完成提取，此处仅组装到 JSON 对象。）

#### treatments.medications（#27）

**来源**: `prescriptions.csv`。

**过滤**: `drug_type = MAIN`（排除 BASE 和 ADDITIVE），`drug` 去首尾空白后非空。

**全时序保留**: 保留同一药物的全部处方记录（按 `starttime` 升序），不丢弃剂量调整。与 Lab 全时序同理——住院期间的剂量变化（如万古霉素 1g q12h -> 500mg q8h）是重要的治疗决策信息。每条处方保留 `starttime` / `stoptime`（处方有效区间，不是 eMAR 给药时刻）。

**输出**: JSON 对象数组，固定属性 `{drug, prod_strength, form_rx, dose_val_rx, dose_unit_rx, route, doses_per_24_hrs, starttime, stoptime}`。

#### treatments.procedures（#28）

**来源**: `procedures_icd.csv` + `d_icd_procedures.csv`。

**过滤**: `icd_code` 非空，`icd_version` 为 9 或 10，能连接到非空 `long_title`。

**去重**: 相同 `icd_code + icd_version` 只保留 `chartdate` 最早的一条。

**排序**: 按 `chartdate` -> `seq_num` -> `icd_version` -> `icd_code` 升序。

**输出**: JSON 对象数组，固定属性 `{procedure_name, icd_code, icd_version}`。

### 5.3 Stage 6: 科室/去向/生命体征

#### demographics.admission_type（#5）+ disposition.admission_location（#30）+ disposition.discharge_location（#31）

这三个字段直接从 `admissions.csv` 中与 `hadm_id` 同行读取:

| # | 字段路径 | admissions 列 | 必需性 |
|--:|---|---|---|
| 5 | demographics.admission_type | `admission_type` | 必需（空则排除 Visit） |
| 30 | disposition.admission_location | `admission_location` | 非必需 |
| 31 | disposition.discharge_location | `discharge_location` | 非必需 |

**实现**: 在 Stage 0 加载 admissions 时即可读取这些列，无需额外源表扫描。

#### disposition.primary_service（#29）

**来源**: `services.csv`。

**关联**: `hadm_id` 匹配，`subject_id` 一致。

**选择**: 按 `transfertime` 升序取最后一条记录的 `curr_service`。

**缺失**: 无 services 记录时写 null。

#### disposition.ed_disposition（#32）

**来源**: `edstays.csv`。

**关联**: `edstays.hadm_id` 等于当前 Visit。

**选择**: 取 `disposition` 列值。如多条记录（罕见），取 `intime` 最晚的一条。

**缺失**: 无 ED 关联时写 null。

#### 生命体征组（#6-#14）

**关联链**:

```text
admissions.hadm_id -> edstays.hadm_id -> edstays.stay_id
edstays.stay_id -> triage.stay_id     (temperature~acuity)
edstays.stay_id -> vitalsign.stay_id  (rhythm)
```

**triage 提取**（#7-#13）:

| # | 字段路径 | triage 列 | 解析 |
|--:|---|---|---|
| 7 | vitals.temperature | temperature | float，无法解析时写 null |
| 8 | vitals.heartrate | heartrate | float |
| 9 | vitals.resprate | resprate | float |
| 10 | vitals.o2sat | o2sat | float |
| 11 | vitals.sbp | sbp | float |
| 12 | vitals.dbp | dbp | float |
| 13 | vitals.acuity | acuity | int |

**rhythm 提取**（#14）: 从 `vitalsign` 表按 `stay_id` 关联，取首次非空 `rhythm` 值。

**vitals.source**（#6）: 当 #7-#14 任一非空时写 `"triage"`；全部为空时写 null。

**覆盖率**: 46.8% 的 eligible Visit 有 triage 数据。无 triage 时 #7-#14 写 null，#6 写 null。

## 六、输出格式

### 6.1 文件与粒度

- 唯一输出文件为 `rwd_benchmark_visits.jsonl`。
- 每个 eligible `hadm_id` 恰好一行 JSON，`hadm_id` 在文件内唯一。
- 输出保留 admissions 源文件顺序（候选顺序）。
- 每行是一个完整的 JSON 对象，顶层 8 个分组：identifiers / demographics / vitals / narrative / investigations / diagnoses / treatments / disposition。结构见字段规范 §四。

### 6.2 通用存储规则

- JSONL 文件使用 UTF-8 编码，换行符 `\n`。每行是一个完整的 JSON 对象（一个 visit），行间无分隔符。
- `subject_id`、`hadm_id`、`diagnoses.primary.icd_code` 按字符串处理，保留前导零。
- 标量非必需字段缺失时写 JSON `null`。
- 集合字段无元素时写空数组 `[]`；investigations 写 `{"laboratory":[],"radiology":[],"cardiology":[],"respiratory":[]}`。
- JSON 对象的固定属性必须完整；源字段缺失时保存 JSON `null`，有效字符串保存为 JSON 字符串，有效数值保存为 JSON 数值。
- 生命体征数值字段（vitals.temperature~acuity）保存数值或 null；源值无法解析为数值时写 null。
- `vitals.rhythm` 保存文本或 null。
- `vitals.source` 当任一生命体征非空时写 `"triage"`；全部为空时写 null。
- `narrative.allergies` 中 `No Known Allergies / Adverse Drug Reactions` 是有效 str，不视为缺失。
- 文本字段保留内部换行。
- 体积估算：~40KB/visit x ~30 万 eligible visit ~ 12GB（gzip 后约 2.5GB）。

## 七、质量验证

### 7.1 结构验证

抽取完成后对输出 JSONL 执行以下验证，任一失败则报错终止:

| 检查项 | 规则 |
|---|---|
| JSON 合法性 | 每行是合法 JSON 对象，可被 `json.loads` 解析 |
| 顶层分组 | 每行 JSON 包含全部 8 个顶层键：identifiers, demographics, vitals, narrative, investigations, diagnoses, treatments, disposition |
| 行唯一性 | `identifiers.hadm_id` 非空且不重复 |
| 行顺序 | 输出行的 `hadm_id` 在 admissions 中的候选顺序单调递增 |
| 必需字段 | identifiers.subject_id, identifiers.hadm_id, demographics.age_at_encounter, demographics.sex, demographics.admission_type, narrative.chief_complaint, diagnoses.primary.icd_code, diagnoses.primary.diagnosis_name, diagnoses.primary.icd_version 均非 null |
| 年龄范围 | demographics.age_at_encounter >= 18 |
| 性别值 | demographics.sex in {M, F} |
| admission_type | 非空 |

### 7.2 JSON 结构验证

逐行解析 JSON 并验证嵌套字段:

| 字段路径 | 验证规则 |
|---|---|
| investigations | 对象；键集 = {laboratory, radiology, cardiology, respiratory}；laboratory 元素含 {itemid, label, fluid, category, results}，results 元素含 {charttime, value, valuenum, valueuom, ref_range_lower, ref_range_upper, flag, comments}；radiology 元素含 {exam_name, charttime, text, details}；cardiology/respiratory 元素含 {order_subtype, ordertime, poe_detail} |
| diagnoses.primary | 对象；键集 = {icd_code, diagnosis_name, icd_version} |
| diagnoses.other | 字符串数组 |
| treatments.medications | 数组；每个对象键集 = {drug, prod_strength, form_rx, dose_val_rx, dose_unit_rx, route, doses_per_24_hrs} |
| treatments.procedures | 数组；每个对象键集 = {procedure_name, icd_code, icd_version} |

### 7.3 DS 章节一致性验证

验证 DS 章节字段是否来自同一份 DS。检查方法: 对同一 Visit 的 `narrative.discharge_note_full`(#37) 重新解析章节，与 #15-#21 和 #33-#36 的值做子串包含校验（章节内容应出现在全文中）。

### 7.4 运行时统计

抽取完成后输出以下统计:

| 指标 | 说明 |
|---|---|
| candidate_count | admissions 候选总数 |
| eligible_count | 通过全部纳入条件的 Visit 数 |
| 各阶段排除数 | Stage 1/2/3 分别排除了多少候选 |
| 字段填充率 | 37 个字段各自的非 null 比例 |
| vitals 覆盖率 | #7-#14 非空的 Visit 比例 |
| investigations.laboratory 平均项目数 | 每个 eligible visit 的平均 lab 项目数 |
| FU 不可用率 | discharge_note_full 中 Follow-up Instructions 内容为 `___` 的比例 |
| 平均行大小 | 每 visit JSON 行的平均字节数 |

## 八、错误处理

### 8.1 全局终止条件

以下错误终止整个抽取，不跳过、不兜底:

| 错误类型 | 条件 | 原因 |
|---|---|---|
| 基础 ID 错误 | admissions 中 subject_id 或 hadm_id 为空 | 数据完整性破坏 |
| hadm_id 重复 | admissions 中同一 hadm_id 出现多次 | 违反唯一性 |
| subject 关联冲突 | 任何源表中 subject_id 与 admissions 不一致 | 数据完整性破坏 |
| 源文件缺失 | 16 张必需表中任一不存在 | 环境配置错误 |

### 8.2 Visit 排除条件

以下情况排除单个 Visit，不影响其他 Visit:

| 排除阶段 | 条件 |
|---|---|
| Stage 1 | 无有效 patients 关联；年龄 < 18 或无法计算；性别无效 |
| Stage 2 | 无有效 seq_num=1 主诊断；多条 seq_num=1；主诊断无法连接字典 |
| Stage 3 | 无符合条件的 DS；所有候选 DS 无明确 Chief Complaint |

### 8.3 字段级缺失处理

非必需字段缺失时按统一规则表示缺失，不影响 Visit 纳入:
- 标量字段写 JSON `null`
- JSON 数组字段写 `[]`
- investigations 写 `{"laboratory":[],"radiology":[],"cardiology":[],"respiratory":[]}`

### 8.4 禁止操作

以下操作在任何阶段均禁止:
- 从其他 Visit、同一患者的其他住院或 LLM 推断补全字段值
- 跨 DS 合并章节内容
- 将 ICD-9 转换为 ICD-10 或反向
- 将 `note_type=AD` 补充记录纳入 DS 候选集
- 从 follow-up instructions（已不可用）提取离院指导内容
- 根据 age_at_encounter 计算"年龄段"并替代原始年龄
- 标准化、翻译或改写任何源文本值
- 在抽取层实现信息隔离（隔离是出题层职责）

## 九、与现有实现的差异

现有 `rwd_pipeline/extraction/` 代码实现 17 字段的抽取管线。本规范定义的 37 字段管线需要在现有基础上新增以下能力:

### 9.1 需新增的管线阶段

| 阶段 | 现有实现 | 需新增 |
|---|---|---|
| Stage 0 | 加载 admissions（仅 subject_id, hadm_id, admittime） | 同时读取 admission_type, admission_location, discharge_location |
| Stage 4 | 解析 5 个 DS 章节 | 扩展为解析 12 个 DS 章节 + 保存全文 |
| Stage 5 | investigation_orders + investigation_reports 分离 | 合并为单一 investigations 字段，Lab 保留全时序 |
| Stage 6 | 不存在 | 新增: services 提取、ED 关联与 triage/vitalsign 提取、ed_disposition 提取 |

### 9.2 需新增的数据源

| 表 | 现有实现 | 需新增 |
|---|---|---|
| admissions | 仅 3 列 | 增读 4 列（admission_type, admission_location, discharge_location） |
| services | 未使用 | 新增 |
| edstays | 未使用 | 新增 |
| triage | 未使用 | 新增 |
| vitalsign | 未使用 | 新增 |

### 9.3 需修正的规则

| 规则 | 现有实现 | 修正 |
|---|---|---|
| investigations 来源 | investigation_orders(Lab+Imaging) + investigation_reports(首次结果) | investigations 合并字段：Lab 全时序 + Radiology + Cardiology + Respiratory |
| Lab 项目识别 | 依赖 poe.order_subtype（几乎全空） | 改为 labevents.itemid + d_labitems.label |
| discharge_record 来源 | Follow-up Instructions | Discharge Instructions |
| 输出格式 | CSV (17 列) | JSONL (37 字段，8 个顶层分组) |

### 9.4 输出 schema 变更

现有 `OUTPUT_COLUMNS` 为 17 列 CSV。需重构为 JSONL 输出，每行一个 JSON 对象，顶层 8 个分组。`build_output_frame` 和 `validate_output` 需相应更新为 JSON 组装和 JSON 结构验证。
