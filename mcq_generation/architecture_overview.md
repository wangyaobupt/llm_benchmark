# RWD Clinical Benchmark MCQ 生成架构总览

## 1. 文档定位

本文档对 MCQ 生成子系统做跨文档的整体梳理：设计思路、管线骨架、模块职责和当前缺口。读者应先从本文建立整体认知，再按需要进入以下细节文档：

- `question_types.md` — 五类题型规范 + EHR 字段表
- `mcq_generation_design.md` — 题型 1（检查检验选择题）的 10 阶段实现规范

本文不重复细节文档中的统计量定义、Schema 字段或验收标准，只提供结构层面的认知地图。

## 2. 顶层框架：一条临床决策链拆成五道题

五类题型沿着临床就诊的自然时间线排布，每一道题都锁住流程中的一个决策点：

```text
患者信息 → ① 检查检验选择 → ② 临床诊断 → ③ 治疗处置 → ④ 转诊科室 → ⑤ 离院指导
```

每个题型有明确的**答案来源字段**和**题干信息字段**，两者严格分离——答案来源字段不能泄漏进题干。比如题型 1 的答案是 `investigation_orders`（检查医嘱），而诊断、检查结果、治疗方案等"后验信息"一律不能进题干，否则等于提前泄露了答案。

五类题型共享同一套通用规则：A-D 四选一单选最佳答案、合成病例（不复制真实患者）、安全优先（不稳定生命体征不得配常规门诊选项）。`question_types.md` 定义的是这些通用规则和每个题型的字段表。

## 3. 核心设计原则：统计答案先于语言生成

这是整个架构的底层判断。题目问的不是"指南推荐什么检查"，而是：

> 给定这组患者特征，真实世界数据中最可能被选择的是哪项检查？（P(y|X) 排名第一）

这个选择带来三个架构后果。

**第一，答案由数据统计决定，不由 LLM 决定。** 先从 11687 条 visit 中挖掘条件规则 X→y，经过统计检验确认为稳健关联后，rank-1 的检查项就是正确答案。LLM 拿到的是已经锁定好的选项和正确位置，它的唯一任务是写一段合成场景的文字。

**第二，LLM 被严格隔离在答案确定之外。** 模型只输出 `stem`（题干）和 `rationale`（一句话理由）。它不能增删选项、不能改正确答案位置、不能添加规则之外的患者事实、不能把"观察性关联"说成"指南推荐"或"因果关系"。

**第三，最小化模型输入。** 发给 LLM 的 payload 只有标准化条件特征名、固定选项和少量聚合统计量——没有患者标识、没有病历原文、没有可识别信息。

## 4. 题型 1 的管线：10 个阶段，3 层门禁

```text
                    数据层（确定性）
rwd_benchmark_visits.csv
  │
  ├─ Stage 0  隐私校验 + 输入契约验证
  ├─ Stage 1  临床特征标准化（年龄→age_band，主诉→symptom 等）
  ├─ Stage 2  检查目录标准化（raw_names → InvestigationConcept）
  ├─ Stage 3  构建 visit 事务（features + outcomes）
  ├─ Stage 4  条件规则挖掘（8 道统计硬门槛）
  ├─ Stage 5  干扰项选择 + A-D 位置锁定
  │
  │           生成层（LLM 调用）
  ├─ Stage 6  LLM 生成合成题干 + 理由
  ├─ Stage 7  程序级生成校验（12 条检查）
  │
  │           审核层（独立隔离）
  ├─ Stage 8  独立自动审题（独立请求 + 独立 prompt）
  ├─ Stage 9  人工审核队列
  └─ Stage 10 导出 gold（fail-closed）
```

这三层是设计的骨架。

**数据层全部确定性、可复现。** 同样的输入事务 + 同样的阈值配置，产生完全相同的 accepted/rejected 规则集、相同的 `rule_id`、相同的干扰项和答案位置。这层不碰 LLM。

**生成层是唯一需要 LLM 的地方，且被严格约束。** LLM 只看到条件特征名和选项，输出经过 12 条程序校验（答案不能出现在题干里、不能有 CJK 字符、不能有真实日期、不能与源文本高重合等），不过就丢弃。

**审核层是独立的第二道 LLM + 人工，与生成隔离。** 自动审题用独立请求和独立 prompt，只返回结构化裁定（9 个布尔项 + accept/reject），不能修改题目。只有自动通过 + 人工 approved 的题才进 gold，任何环节缺失都 fail-closed 不发布。

## 5. 规则挖掘：8 道统计硬门槛

这是"统计答案"的质量保证层。每条候选规则 X→y 必须同时通过：

| 门槛 | 默认值 | 防的是什么 |
|---|---|---|
| `min_x_support` | 5 | 条件样本太少 |
| `min_xy_support` | 4 | 共现太少 |
| `min_smoothed_probability` | 0.60 | 条件概率不够高 |
| `min_lift` | 1.20 | 不比基线好 |
| `min_wilson_lower` | 0.35 | 小样本下区间太宽 |
| `max_fdr_q` | 0.05 | 多重检验后不显著 |
| `min_bootstrap_stability` | 0.80 | 第一名不稳定 |
| `min_probability_gap` + `min_score_ratio` | 0.15 / 1.25 | 与第二名区分度不够 |

宽松阈值可以跑，但结果标记 `exploratory`，不能进 gold。所有阈值预登记，不可临时调松来凑数。

## 6. 模块职责划分

设计文档建议的子系统拆分，核心是**职责不可合并**：

| 子系统 | 主要职责 |
|---|---|
| `schemas` | 全部版本化严格数据契约（禁止额外字段） |
| `source` / `phenotype` | 输入解析 + 临床特征提取 |
| `catalog` | 检查名称标准化 + 别名组 |
| `mining` | 事务构建 + 统计量 + 规则排名 + 门槛 |
| `generation` | 干扰项 + 答案位置 + LLM 题干 + 生成校验 |
| `privacy` | payload 最小化 + 禁止字段 + 文本隐私检查 |
| `review` | 独立结构化自动审题 |
| `pipeline` | 阶段编排 + 状态 + 人工队列 + gold 导出 |
| `audit` / `client` | 原子产物 + 缓存 + 重试 + API 审计 |

关键红线：**统计规则选择、模型语言生成、审核裁定三者不能合并到同一个不可审计的调用中。** 这条线保证了每一步都可以独立追溯、独立复现、独立审计。

每一道 gold 题可以完整回溯到：来源规则 → 统计量（n_xy、lift、Wilson、FDR 等）→ 生成模型和 prompt 版本 → 审核模型和审核记录 → 人工决定。`manifest.json` 记录数据哈希、模型 ID、阈值配置、prompt/schema 版本，保证可复现。

## 7. 当前结构性缺口

```text
题型 1（检查检验选择）：  完整统计管线设计，零实现代码
题型 2-5（诊断/治疗/转诊/离院）：  题型规范 + EHR 字段表，无管线设计
上游 rwd_standardization 模块：  spec + test 就绪，代码缺失
```

题型 1 的实现是整个项目的第一块代码，但它依赖的上游数据管线（standardization）还没落地。这是当前推进的物理瓶颈。
