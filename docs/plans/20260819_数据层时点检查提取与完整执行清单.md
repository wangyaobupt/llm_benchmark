## 0. 要先解决的问题

当前得不到金标准，不是因为 MIMIC 没有医嘱时间，而是**没有一张可查询的时点检查表**。

已有事实：

- `clean_clinical_archive` 的 `poe_timeline` 已经有 `event_time`、`action`（create/change/discontinue）、`order_type` / `order_subtype`、`chain_root_poe_id`。
- `event_pipeline` 已把 POE 变成 `laboratory_ordered` / `imaging_ordered` / `clinical_ordered`，把 labevents 变成 `laboratory_resulted`（`charttime` / `storetime`）。
- 旧 phenotype 是 **visit 级长表**：一次住院压成一组特征，目标窗是整次住院。所以问「这一刻开了什么检查」必然答不出。
- 规范事件把 `chain_root_poe_id`、`order_subtype`、`specimen_id` 埋在 `value_structured_json` 或源 JSON 里，顶层查不到。
- `clinical_ordered` 混进药品、IV、General Care、ADT，不能当检查轨。
- 现有 `episodes.py` 按 `poe_id` 分组，并且会丢掉后来 Inactive / cancel 的历史 create。

因此本阶段的数据层目标只有一句：

```text
给定 (subject_id, hadm_id, index_time)
→ 该时点发生了哪些合格 investigation 开单动作
→ 同一时刻之前，哪些检查/结果已经发生且已经可见
```

在这张表稳定之前，不挖规则、不出题、不审 134 道旧候选。

## 1. 先冻结的语义（不做对就不要写代码）

| 问题 | 本轮答案 | 禁止的说法 |
|---|---|---|
| 「做了什么」指什么 | 一次可观察的 **开单动作**（POE create，必要时含有内容变化的 change） | 整次住院做过的全部检查；「医生下一步会不会开单」 |
| 时间点是什么 | 该 investigation episode 的 `initial_order_time` | 出院时间；任意结果回报时间 |
| 生命周期按什么聚 | `chain_root_poe_id` | 单个 `poe_id` |
| 后来变成 Inactive | 历史 create **保留** | 当作从没开过 |
| Lab 项目级医嘱 | MIMIC **没有**。只能做 `generic_lab_order` 或 `lab_result_proxy` | 用 labevents 邻近关系反推「开了 CBC」 |
| `clinical_ordered` | 只是 POE 容器，必须过 eligibility | 凡是 clinical_ordered 都是检查 |
| 影像粒度 | 源里有什么写什么（常是 Radiology / CT Scan） | 补出 CT head / CT chest |
| 结果 vs 开单 | 分开两张语义，不混进同一金标准 | 用结果出现证明当时开了该项目 |

主任务固定为：

```yaml
decision_semantics: conditional_order_choice
```

含义：已知该时点发生了一次合格开单，记录同一比较类、同一 burst 内实际开出的 candidate。  
不是预测「会不会开单」。

## 2. 可复用数据层目标形态

不要重跑 27M 主事件表。在现有 `clinical_event/1.2.0` + 1,000 例聚合 + POE 时间线之上，做**派生投影**。

```text
① 已完成：raw JSONL → 解码/POE 时间线 → event 1.2.0 → 1,000 例聚合
② 本阶段新增（可复用、可查询）：

encounter_clocks.parquet
    一次住院一行；ED/住院时钟分开，不 coalesce

investigation_actions.parquet
    一行一个 POE 动作（create/change/discontinue）
    顶层暴露：hadm_id, event_time, available_time,
    chain_root_poe_id, poe_id, poe_seq, action,
    order_type, order_subtype, content_specificity,
    eligibility, candidate_id, candidate_specificity

investigation_episodes.parquet
    一行一个检查 episode（按 chain 折叠）
    initial_order_time, last_action_time,
    was_later_cancelled, terminal_status,
    candidate 不变则 change 不新开 target

lab_result_episodes.parquet
    按真实 specimen_id 分组的结果 episode
    collection_time_proxy = charttime
    available_time = storetime
    不叫 specimen_received_time
    不反推 specific lab order

visible_facts_at_index.parquet  （可后于 actions 做）
    对每个 index_time：event_time < index
    AND available_time <= index
    且非 post_hoc
```

验收句：对任意抽样 hadm，能列出「08:17 开了 ECG；08:17 前可见的是主诉和分诊生命体征，还不可见 09:02 入库的肌钙蛋白」。

## 3. 完整计划清单

### A. 数据层：时点检查可提取（现在就做）

闸门：A 全部通过前，不进入统计 / TF-IDF / 出题。

#### A0. 范围与输入

- [ ] 固定本阶段只读输入：1,000 例已验收聚合 + 对应 clinical-readable JSONL（含 `poe_timeline`）+ 必要时 raw labevents 的 `specimen_id`
- [ ] 不读 phenotype 特征表，不读旧 V2 规则/题目
- [ ] 不重跑 39,036 全量 event 1.2.0
- [ ] 输出写新目录，禁止原地覆盖已成功产物

#### A1. 把「开单动作」从 payload 提到可查询表

现有缺口：`orders.py` 把 `poe_id` / `order_subtype` / `relations.chain_root_poe_id` 放进 `value_structured_json`。

- [ ] 从 `poe_timeline` 或规范化事件投影 `investigation_actions`
- [ ] 顶层字段至少：`subject_id, hadm_id, event_id, event_time, available_time, poe_id, poe_seq, chain_root_poe_id, action, order_type, order_subtype, content_specificity, status, source_event_id`
- [ ] `successor` / `chain_complete` / 终态标为 `retrospective_only`，formal 查询不得当可见证据
- [ ] 测试：同一 chain 跨多个 `poe_id`；`chain_root` 稳定

#### A2. 生命周期按 chain 折叠，而不是按 poe_id

现有缺口：`source_grouping.py` 用 `poe_id`；`episodes.py` 丢掉 cancel/inactive。

- [ ] grouping key = `stable_hash(hadm_id, chain_root_poe_id)`
- [ ] create：即使后来 Inactive，仍是 observed ordering
- [ ] change：仅当 candidate 内容可见变化时才可能新 target；`change_without_observable_delta` 只留 lineage
- [ ] discontinue/cancel：关闭 interval，**不删除**已发生的 create
- [ ] 测试：`test_create_remains_observed_if_later_inactive`；`test_cancel_does_not_delete_prior_create`

#### A3. 检查资格目录（否则时点表全是药和护理）

现有缺口：非 Lab/Radiology 全部进 `clinical_ordered`。

- [ ] 在 1,000 例上统计 `order_type × order_subtype` 频数
- [ ] 写 `investigation-order-eligibility.yaml` 草案：`eligible_investigation` / `monitoring_only` / `excluded_non_investigation` / `review_required`
- [ ] 预标注：Medications / IV therapy = 排除；ECG / Echo = 合格；Telemetry / Vitals = 待审
- [ ] 临床扫一眼后再冻；不得用单例 hadm 定白名单
- [ ] 测试：用药医嘱不得进入 investigation episode

#### A4. 影像与 Lab 的可提取粒度写死

- [ ] 影像：`candidate_specificity = category | subtype | entity`；没有 body site 不得补
- [ ] `generic_lab_order`：只保留 MIMIC 真实支持的泛化 Lab 开单
- [ ] `lab_result_proxy`：另表；用 `specimen_id` 分组；缺 ID 标 `missing_in_source`，禁止用时间邻近伪造
- [ ] `charttime` 只叫 `collection_time_proxy`；`storetime` 才是结果可见时间
- [ ] 测试：order 与 result 不得按时间对齐成同一 gold

#### A5. 时点查询接口（数据层完成的定义）

- [ ] 实现唯一查询：`list_investigations_at(hadm_id, index_time) -> actions/episodes`
- [ ] 实现唯一查询：`list_visible_facts(hadm_id, index_time, query_start) -> facts`
- [ ] 可见性：`event_time < index` AND `available_time <= index`；未知时间主分析拒绝
- [ ] 结果类允许「发生早于 query_start，但 available_time 落入窗口」
- [ ] 抽 20 个 hadm 人工可读 trace：Decision / 当时开了什么 / 当时已可见 / 被排除及原因
- [ ] 输出 `time-policy-coverage`、`poe-subtype-audit`、`poe-lifecycle-audit`、`specimen-audit`

**A 阶段完成标准**

1. 给定时间点，能列出合格检查开单，而不是整次住院袋。
2. 药品/输液不会出现在检查列表里。
3. Inactive 不会抹掉当时开单。
4. 不能把「开了 Lab」说成「开了肌钙蛋白」。
5. 1,000 例上上述四张审计表可解释。

## 6. 本周顺序

```text
1. A1 动作表（能列出该 hadm 每个开单时刻的 order_type/subtype/action/chain）
2. A2 chain 折叠（Inactive 仍能看到当时 create）
3. A3 1,000 例 order_type×subtype 频数 + eligibility 草案

5. A5 时点查询 + 20 条 trace

```

第一步验收：对已有聚合样本（例如 `hadm-26691544` 或 `hadm-28234402`）打出一张时间排序的检查开单表，人工能读懂「这一刻开了什么、属于哪条 chain、后来有没有被改/停」。这张表还不存在，正是现在做不出时点金标准的原因。
