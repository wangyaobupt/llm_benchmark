# 一次住院信息分层与时点检查读法

> 日期：2026-08-19  
> 回答两件事：  
>
> 1. 为什么时点投影 JSON 里看不到「具体检查项目」；  
> 2. 一次住院的全部信息应该读一份大 JSON，还是从多个文件拼。

结论先说：

- **时点投影不是住院病历全文。** `data/derived/investigation_timepoint/` 只回答「这一刻开了什么检查 / 哪些结果后来可见」。
- **具体化验名在结果层，不在开单层。** MIMIC 的 POE Lab 医嘱几乎只有 `order_type=Lab`，没有 CBC / 肌钙蛋白。项目名在 `labevents` 结果里。
- **一次住院应分层读多个文件，用 `hadm_id` / `event_id` / `source_record_id` 连接。** 不要把全部源行塞进检查投影 JSON。整次住院的事件总览已经另有 extract。

---

## 1. 先分清三种「检查信息」

| 语义 | 源表 | 这一层能写到多细 | 能不能当「当时开了这个检查」 |
|---|---|---|---|
| 开单动作 | `hosp.poe` / `poe_timeline` | Lab 只有「Lab」；影像常到 `CT Scan` / `General Xray`；心内科可到 `ECG` / `Echo` | 可以，这是开单金标准 |
| 检验结果 | `hosp.labevents` | 到具体项目：Bicarbonate、ALT、Troponin | **不可以。** 这是结果回报，时间是抽血代理 / 入库时间 |
| 影像报告 | `note.radiology` | 报告文本，不是开单目录 | 不可以当开单 |

`hadm-28234402` 的投影已经按这个边界做事：

```text
开单 catalog（investigation_episodes.json）
  ECG、Echo、Lab、General Xray、MRI、CT Scan、Ultrasound

结果层（investigation_actions.json 里 track_id=lab_result_proxy）
  Bicarbonate、Alanine Aminotransferase (ALT)、……具体项目名都在
```

如果你只看 `investigation_episodes.json` 或 `catalog`，会觉得「没有具体检查」。那是因为 **episode 当前只折叠了开单链**。Lab 开单在源数据里就叫 `Lab`，并打了 `ORDER_CONTENT_CATEGORY_ONLY`。这不是提取丢了字段。

同一例里，结果动作已经有项目名，例如：

```text
event_time     2142-04-29T05:55:00    采集时间代理（charttime）
available_time 2142-04-29T06:56:00    结果可见（storetime）
candidate_name Bicarbonate
track_id       lab_result_proxy
```

它的意思是：大约 05:55 抽了这管标本，06:56 碳酸氢盐结果入库。  
**不能改写成：05:55 医生开了碳酸氢盐医嘱。**

这份结果在 `hadm-28234402` 上没有进 episode，是因为该 extract 的事件顶层没有 `specimen_id`，分组状态是 `missing_in_source`。完整聚合（`hadm-26691544-aggregated-complete.json`）里带了 `raw_record_json`，才能把同标本结果捆在一起。即使用上标本键，结果 episode 仍然是 **result-proxy**，不是项目级 lab order gold。

影像同样不能补细：源里是 `Radiology / CT Scan`，不能写成 CT head / CT chest。

---

## 1.1 时间是准的，项目名不在开单行上

临床医嘱单上确实会同时写「几点开、开了哪些项目」。MIMIC 把这两件事拆进了两张互不外键连接的表。

用 `hadm_id=26691544` 的真实行：

**开单（`hosp.poe`，有精确开单时间，没有项目清单）**

```text
ordertime      2126-06-20 00:43:40
order_type     Lab
order_subtype  null
poe_detail     []          ← 空，没有 CBC / 肌钙蛋白 / 肝功
transaction    New
```

可读文本就是「新开检验医嘱」。时间精确到秒，内容只有类别 `Lab`。全队列约 97 万条 Lab 开单里，99.99% 都是这种 `category_only`。

**结果（`hosp.labevents`，有具体项目和另一套时间）**

```text
itemid / 名称   50856 Acetaminophen
charttime      2126-06-19 19:55:00   标本采集时间代理
storetime      2126-06-19 21:00:00   结果在实验室系统可见
specimen_id    有
poe_id         无（这张表不指向那条 Lab 医嘱）
```

所以：

| 问题 | 答案 |
|---|---|
| 化验有没有精确时间？ | 有。开单有 `ordertime`；结果有 `charttime` / `storetime` |
| 具体项目能不能精确到时间？ | 能，但是精确到**结果时间**，不是开单时间 |
| 能不能说「00:43:40 开了对乙酰氨基酚血药浓度」？ | 不能。00:43:40 那张 POE 没有项目列表；19:55 那条是结果行 |

`labevents` 没有 `poe_id`，不能靠时间邻近把结果项目接回「Lab」开单。接回去就是在猜医嘱单内容。

影像、心电图不是这个结构：POE 上已经有 `Radiology / CT Scan`、`Cardiology / ECG` 和 `ordertime`，这些才是「具体检查 + 开单时刻」。

若研究问题改成「某个具体化验结果何时可被看到」，应走 `lab_result_proxy`（`charttime` / `storetime`），不要改称项目级 lab order gold。

---

## 2. 不要指望一份检查 JSON 装下整次住院

`python -m data_pipeline.investigation_selection` 的输出是**检查决策视图**，故意丢掉了：

- 主诉、生命体征、用药、出入量、转科、出院诊断
- 文书全文
- 原始 CSV 行

这是对的。把 1 万多条事件和整行 `raw_record_json` 再塞进检查投影，会把「当时开了什么」重新淹没，文件也会大到无法审。

一次住院的「全部信息」已经在更早的层里。应按角色读，不要合并成一个万能 JSON。

---

## 3. 一次住院读哪几层

用 `hadm_id` 当主键。需要原文或源行时，再用 `event_id` → `source_record_id` / `raw_row_ref`。

```text
原始归档 JSONL          一次住院一行，32 张表原样嵌套
        │
临床可读 JSONL          字典解码 + poe_timeline（chain_root、action、order_type）
        │
规范化事件 parquet      一行一个临床事件（约 47 列）
        │
无损聚合 parquet        事件 + 原文 + 整行 JSON（1,000 例已验收）
        │
单次住院 extract JSON   给人读的总览（全部 event_kind）
        │
时点检查投影 JSON       只回答开单 / 结果代理 / 当时可见
```

### 3.1 整次住院总览（要「这次住院发生过什么」时读这里）

| 文件 | 里面有什么 | 没有什么 |
|---|---|---|
| `docs/reports/hadm-28234402-event-aggregated.json` | 该次住院 **全部 835 条**规范化事件，按 `event_kind` 分组：主诉、生命体征、用药、开单、结果、转科、出院后诊断…… | 多数事件没有嵌整行 raw JSON |
| `docs/reports/hadm-26691544-aggregated-complete.json` | 该次住院 **全部 13,782 条**事件，并且带 `source_text`、`raw_record_json`、`clinical_readable_record_json` | 文件很大，适合审计，不适合当检查金标准 |
| `docs/reports/hadm-28234402-normalized-events.json` | 与上类似的规范化事件平铺 | 无聚合补回的原文 |

这两份 report extract 才是「一份 JSON 看完整住院」。它们已经存在，时点投影没有、也不应该替代它们。

自己从 1,000 例聚合再抽一例：

```powershell
.\.venv\Scripts\python.exe scripts\extract_aggregated_hadm.py `
  --aggregation-dir data\test_1000_0812\event_pipeline_output\aggregation `
  --hadm-id 26691544 `
  --output docs\reports\hadm-26691544-aggregated-complete.json
```

### 3.2 批量、可检索的全住院层（做统计时读这里）

| 文件 | 用途 |
|---|---|
| `...\normalization\normalized_events.parquet` | 全队列 / 批次的事件表，按 `hadm_id` 过滤 |
| `...\aggregation\processed_events.parquet` | 事件 + 五类 `source_text`（主诉、报告摘录等） |
| `...\aggregation\raw_source_records.parquet` | 每个源行一行，含完整 JSON |
| `...\aggregation\traceable_events.parquet` | 事件内嵌源行，审计用 |

当前全队列事件在冠心病 39,036 住院上已有；**全队列聚合还只有 1,000 例**。所以「带原文的整次住院」目前以 1,000 例批次为准。

### 3.3 检查时点层（要「这一刻开了什么」时读这里）

目录：`data/derived/investigation_timepoint/hadm-<id>/`

| 文件 | 读它干什么 |
|---|---|
| `investigation_actions.json` | 每一个开单动作和每一个检验/微生物结果一行。开单细到源数据允许的粒度；结果有具体项目名 |
| `investigation_episodes.json` | 按 POE chain 折叠后的检查 episode + 开单 catalog |
| `poe-subtype-audit.json` | 这次住院 `order_type × subtype` 频数和资格 |
| `timepoint-trace.json` | 指定 `--index-time` 时：这一刻开了什么、此前可见什么、为何排除 |
| `timepoint-traces.json` | 未指定时点时，自动抽最多 20 个开单时点的 trace |
| `manifest.json` | 计数 |

过滤办法：

```text
只要开单金标准
  actions.eligibility == eligible_investigation
  且 track_id ∈ {imaging_order, clinical_order, generic_lab_order}

要具体化验名（结果代理，不是医嘱）
  actions.track_id == lab_result_proxy

要当时已看见的主诉/生命体征/先前结果
  读 timepoint-trace.json 的 included_evidence
  或回到 3.1 的全事件 JSON，用 query.list_visible_facts
```

### 3.4 原始嵌套住院（要对回 MIMIC 表时读这里）

| 文件 | 用途 |
|---|---|
| 原始 admission JSONL（`mimic_admission_raw`） | 32 张表原样字符串，无派生 |
| 临床可读 JSONL（`mimic_admission_clinical_readable`） | `itemid_decoded`、`poe_timeline`、note 正文 |

一行就是一次住院的全部源表。适合对账，不适合直接做时点金标准。

## 4. 应该「分别提取」还是「合成一份」

**分别提取，按问题选文件。** 键统一即可。

```text
hadm_id                         一次住院
event_id                        一条规范化事件
source_record_id / raw_row_ref  回到源行
chain_root_poe_id               一条医嘱生命周期
specimen_id                     一管检验标本（仅结果层）
```

推荐读法：

| 你想知道 | 打开 |
|---|---|
| 这次住院从头到尾发生过哪些事 | `hadm-*-event-aggregated.json` 或 `*-aggregated-complete.json` |
| 08:02 开了什么检查 | `timepoint-trace.json` 或 `list_investigations_at(...)` |
| 08:02 之前医生能看见什么 | 同一份 trace 的 `included_evidence` |
| 肌钙蛋白数值是多少、几点出的 | 全事件 JSON 或 actions 里 `lab_result_proxy` + `laboratory_resulted` |
| 出院诊断 / 用药 / 生命体征 | 全事件 JSON，按 `event_kind` 过滤 |
| 放射报告原文 | 聚合层 `source_text` 或临床可读 JSONL 的 note |
| 源表那一行原始字段 | `raw_source_records.parquet` 或 complete extract 的 `raw_record_json`zx |

**不要做的：**

- 不要把 raw + 全部事件 + 检查投影压成一个新的「超级 JSON」当主产物。`hadm-26691544-aggregated-complete.json` 已经证明这种文件只适合偶尔审计。
- 不要把结果项目名写回开单 episode，假装 POE 开了「Bicarbonate」。
- 不要只读 `investigation_episodes.json` 就判断「数据里没有具体检查」。

若只是给人浏览一次住院，用已有的全事件 extract 即可，不必再生成第三份大 JSON。

---

## 5. 用 hadm-28234402 对一下

该次住院在全事件 JSON 里有 21 种 `event_kind`、835 条事件。  
检查投影从中抽出 612 条开单/结果动作：合格开单 48，药/输液/ADT 等排除 272，结果代理 270。

开单能点名的只有：

- 临床：ECG、Echo  
- 影像：CT Scan、General Xray、MRI、Ultrasound  
- 检验开单：Lab（40 次，全部 category_only）

具体化学/血常规项目出现在结果动作里（Bicarbonate、ALT 等），时间是 `charttime` / `storetime`，标本键在这份较瘦的 extract 上缺失。

因此：

- 「当时开了什么检查」→ ECG / Echo / CT Scan / Lab。Lab 不能再细。  
- 「后来查出什么」→ 回全事件 JSON 或 actions 的 `lab_result_proxy`。  
- 「这次住院还输液、用药、转科了没有」→ 回全事件 JSON，不在检查投影里。

## 6. 常用命令

```powershell
# 整次住院事件总览（已有产物，不必重跑）
# docs\reports\hadm-28234402-event-aggregated.json
# docs\reports\hadm-26691544-aggregated-complete.json

# 从 1,000 例聚合再抽一例完整住院
.\.venv\Scripts\python.exe scripts\extract_aggregated_hadm.py `
  --aggregation-dir data\test_1000_0812\event_pipeline_output\aggregation `
  --hadm-id <hadm> `
  --output docs\reports\hadm-<hadm>-aggregated-complete.json

# 只做检查时点投影（输入用上面的全事件 JSON）
.\.venv\Scripts\python.exe -m data_pipeline.investigation_selection `
  docs\reports\hadm-28234402-event-aggregated.json `
  --output-dir data\derived\investigation_timepoint\hadm-28234402 `
  --index-time 2142-04-28T18:02:32
```

模块说明见 [`data_pipeline/investigation_selection/README.md`](../../data_pipeline/investigation_selection/README.md)。
