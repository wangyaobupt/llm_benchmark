# 出题数据抽取字段规范

> **生成日期**: 2026-08-07
> **修订日期**: 2026-08-07（v2：存储格式改为 JSONL，investigation 字段合并，Lab 全时序保留，抽取层职责纯化）
> **数据版本**: MIMIC-IV v3.1 (hosp/icu) + MIMIC-IV-ED v2.2 (ed) + MIMIC-IV-Note v2.2 (note)
> **设计依据**: 临床决策流程推导 + MIMIC 原始数据实际列结构与值分布验证

---

## 一、文档定位

本文档定义从 MIMIC-IV 抽取的 **visit 级 JSONL 数据**的完整字段结构。每行是一个住院（`hadm_id`）的完整 JSON 对象，包含该次住院的全量临床资料。该数据是五类临床 MCQ 题型的统一数据底座，也可直接用于文本处理训练。

**全部字段的设计起点是临床决策流程，不是任何已有的抽取实现或中间层。** 字段的选择、角色分配和内部结构均从以下流程逐步推导：

```
患者信息 → ① 检查检验选择 → ② 临床诊断 → ③ 治疗处置 → ④ 转诊科室 → ⑤ 离院指导
```

### 1.1 抽取层与出题层职责分离

- **抽取层（本规范定义）**：忠实记录单个 visit 的全量资料，不做任何信息隔离。JSONL 每行一个 visit，字段按分组嵌套。
- **出题层（下游）**：按题型选择性读取字段实现信息隔离。需要隔离时，出题引擎自行决定哪些字段进题干、哪些不读——读取 JSON 字段时跳过即可，不需要抽取层提前过滤。

此架构使数据文件成为中立的全量记录；隔离规则随题型变化时只需改出题引擎配置，不需要重新抽取数据。

## 二、设计原则

### 2.1 信息隔离

信息隔离在**出题层**实现，不在抽取层强制。抽取层记录全量资料；出题引擎按题型选择性读取 JSON 字段实现隔离——答案来源字段在出题时不读入题干即可。

### 2.2 流程推导优先

每个字段的存在理由追溯到临床流程中的一个具体决策需求。没有决策需求的字段不进入数据结构。字段的角色（题干/条件/答案）由其在流程中的位置决定，不由数据存储形式决定。

### 2.3 DS 章节独立提取

出院小结（DS）的每个标准章节提取为独立字段，而非拼接为单一文本。数据验证确认以下标题在 DS note 中稳定出现（5000 条采样）：

| 标题 | 存在率 |
|---|---|
| Chief Complaint | ~100% |
| History of Present Illness | ~100% |
| Past Medical History | ~100% |
| Social History | 97.4% |
| Allergies | 99.9% |
| Physical Exam | ~100% |
| Pertinent Results | ~100% |
| Brief Hospital Course | ~100% |
| Medications on Admission | ~100% |
| Discharge Medications | ~100% |
| Discharge Diagnosis | 95.8% |
| Discharge Condition | ~100% |
| Discharge Instructions | 99.2% |
| Follow-up Instructions | 98.3%（**内容 100% 被去标识化为 `___`，不可用**） |

### 2.4 结构化优先

能从结构化表（admissions / diagnoses_icd / prescriptions / poe / services / triage）直接获取的数据，不从自由文本推断。

### 2.5 生命体征独立属性

体温、心率、呼吸、血压等生命体征作为独立属性（嵌套于 `vitals` 对象下），而非打包为单一文本。原因：出题时常需单独引用某项生命体征（如"血压 90/60"），独立属性便于直接筛选异常值和构造条件题干。

### 2.6 检查检验合并保存

`investigation_orders` 和 `investigation_reports` 合并为单一 `investigations` 字段。原因：抽取层目的是获取全量资料，Lab 的医嘱和结果同源于 labevents，分离只剩冗余。合并后 Lab 按 itemid 聚合，同项目的多次测量保留全时序（`results` 数组），供出题引擎或文本训练理解病情演变。Cardiology/Respiratory 仅有医嘱层信息（无结构化结果表），保存 order_subtype + poe_detail。

### 2.7 JSONL 存储格式

使用 JSONL（JSON Lines）而非 CSV。原因：37 个字段中约 14 个是嵌套 JSON 对象/数组，约 11 个是长文本（DS 章节、影像报告），单个 visit 的全量资料（DS 全文 + ~45 项 lab 时序 + 影像报告）约 30-50KB。JSONL 天然支持嵌套结构，文本字段不需 CSV 转义，是文本训练的标准输入格式。体积估算：~40KB/visit x ~30 万 eligible visit ~ 12GB（gzip 后约 2.5GB）。

## 三、从临床流程推导字段

### 3.1 推导方法

沿临床流程逐步追问："这个决策点需要什么信息？"每个回答映射到一个或多个字段，并确定其角色。角色的定义来自出题需求：

- **题干信息**：构造患者场景时必定的输入
- **条件题干信息**：仅在影响答案判断时加入
- **答案来源**：用于生成标准答案和候选项，不得提前泄漏

### 3.2 患者基础信息层

流程起点是"谁来了、为什么来、来的时候什么状态"。这些信息在五个题型中反复使用，因此是全部题型的共用输入。

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 患者是谁 | 识别和关联 | — | identifiers.subject_id, identifiers.hadm_id | admissions |
| 年龄、性别 | 影响疾病风险和检查/治疗适用性 | ①②③④⑤ 题干 | demographics.age_at_encounter, demographics.sex | patients + admissions |
| 怎么来的 | 紧急程度影响检查优先级和服务层级 | ①④ 条件 | demographics.admission_type | admissions |
| 从哪来 | 就诊途径（急诊/转诊/门诊） | ④ 条件 | disposition.admission_location | admissions |
| 为什么来 | 本次就诊的主要临床问题 | ①②③④ 题干，⑤ 条件 | narrative.chief_complaint | DS -> Chief Complaint |
| 症状如何演变 | 起病方式、持续时间和变化过程 | ① 题干 | narrative.history_of_present_illness | DS -> HPI |
| 既往有什么病 | 影响检查选择、鉴别诊断、治疗安全性 | ① 题干，②③④⑤ 条件 | narrative.past_medical_history | DS -> PMH |
| 社会史 | 吸烟/饮酒/职业影响诊断和治疗 | ①②③ 条件 | narrative.social_history | DS -> Social History |
| 入院前吃什么药 | 影响检查结果解释、重复用药判断 | ① 题干，②③④⑤ 条件 | narrative.medications_on_admission | DS -> Medications on Admission |
| 过什么敏 | 涉及药物时是安全必需件 | ①③⑤ 条件 | narrative.allergies | DS -> Allergies |
| 入院时生命体征 | 判断病情紧急程度 | ①②③④ 条件 | vitals.temperature~acuity, vitals.rhythm | triage, vitalsign |
| 体格检查发现 | 辅助鉴别诊断和治疗决策 | ②③④ 条件 | narrative.physical_exam | DS -> Physical Exam |

### 3.3 题型① 检查检验选择

> **决策点**: 给定患者表现，最应优先选择哪项检查/检验？
> **问的是什么**: 诊断过程中的下一步信息获取

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 实际做了哪些检查、结果如何 | 生成候选答案和标准答案 | **答案** | investigations | labevents + d_labitems; poe + poe_detail; radiology + radiology_detail |

信息隔离（出题层实现）：出题引擎读取 investigations 构造题型①答案时，不读 diagnoses、treatments 字段。

### 3.4 题型② 临床诊断

> **决策点**: 整合症状、体征和检查结果，最可能的诊断是什么？

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 最终诊断是什么 | 生成候选答案和标准答案 | **答案** | diagnoses.primary, diagnoses.other | diagnoses_icd + d_icd_diagnoses |
| 检查检验结果 | 诊断依据（条件题干） | 条件 | investigations.laboratory, investigations.radiology | labevents+d_labitems; radiology+radiology_detail |

信息隔离：Discharge Diagnosis 文本章节不进入题干。

### 3.5 题型③ 治疗处置

> **决策点**: 根据诊断和患者情况，最适当的治疗或处置是什么？

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 实际开了什么药 | 生成药物治疗候选答案 | **答案** | treatments.medications | prescriptions |
| 实际做了什么操作 | 生成手术/操作候选答案 | **答案** | treatments.procedures | procedures_icd + d_icd_procedures |

信息隔离（出题层实现）：出题引擎构造题型③答案时不读 disposition.discharge_medications。

### 3.6 题型④ 转诊科室

> **决策点**: 患者当前应转介至哪个科室或服务？

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 最终由哪个科负责 | 生成候选答案 | **答案** | disposition.primary_service | services |
| 患者实际去了哪 | 生成候选答案（去向层级） | **答案** | disposition.discharge_location | admissions |
| 急诊去向 | 辅助判断急诊后路径 | 条件 | disposition.ed_disposition | edstays |

### 3.7 题型⑤ 离院指导

> **决策点**: 根据治疗经过和离院状态，最适当的离院指导是什么？

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| 给患者的出院指导信 | 提取随访计划、用药建议、危险信号 | **答案** | disposition.discharge_record | DS -> Discharge Instructions |
| 住院治疗经过 | 判断离院指导合理性（条件） | 条件 | disposition.brief_hospital_course | DS -> Brief Hospital Course |
| 出院带药 | 判断用药指导完整性（条件） | 条件 | disposition.discharge_medications | DS -> Discharge Medications |
| 离院时状态 | 判断随访紧迫性（条件） | 条件 | disposition.discharge_condition | DS -> Discharge Condition |

### 3.8 备用层

| 流程需求 | 为什么需要 | 角色 | 对应字段 | MIMIC 来源 |
|---|---|---|---|---|
| DS 完整原文 | 章节解析失败时恢复；按需提取未设独立字段的章节 | — | narrative.discharge_note_full | DS -> text 全文 |
| 生命体征来源标记 | 区分 triage/chartevents 来源，质量评估 | — | vitals.source | 计算字段 |

### 3.9 推导结果

以上推导产生 **37 个字段**（原 38 字段中 investigation_orders + investigation_reports 合并为 investigations）。每个字段的存在理由可追溯到临床流程中的一个具体决策需求，不依赖任何已有抽取实现。

## 六、逐字段抽取规则

### 6.1 患者标识与人口统计（#1-#5）

#### `identifiers.subject_id`（#1）

- **流程需求**: 唯一标识患者，用于关联同一患者的不同住院（不跨住院合并数据）。
- **来源**: `admissions.subject_id`。
- **必需性**: 必需。缺失或与 `patients` 关联失败时排除 Visit。

#### `identifiers.hadm_id`（#2）

- **流程需求**: 唯一标识一次住院，是行的权威主键。所有住院级数据通过 `hadm_id` 关联。
- **来源**: `admissions.hadm_id`。
- **保存格式**: str，保留源值和前导零，不转整数。
- **必需性**: 必需。重复或缺失时排除 Visit。

#### `demographics.age_at_encounter`（#3）

- **流程需求**: 年龄影响疾病风险评分、检查适用性和治疗强度。
- **来源**: `patients.anchor_age` + `patients.anchor_year` + `admissions.admittime`。
- **计算**: `age_at_encounter = anchor_age + year(admittime) - anchor_year`
- **保存格式**: int。结果必须 >= 18，否则排除 Visit。

#### `demographics.sex`（#4）

- **流程需求**: 性别影响疾病患病率、药物禁忌和鉴别诊断范围。
- **来源**: `patients.gender`。
- **保存格式**: str，保留 `M` 或 `F`。无效值排除 Visit。

#### `demographics.admission_type`（#5）

- **流程需求**: 入院类型反映就诊紧急程度。题型①判断检查优先级、题型④判断服务层级时需要此信息。
- **来源**: `admissions.admission_type`。
- **必需性**: 必需。
- **实际值分布**（全库 546,028 条）:

| 值 | 含义 | 计数 |
|---|---|---|
| EW EMER. | 急诊入院 | 177,459 |
| EU OBSERVATION | 急诊留观 | 119,456 |
| OBSERVATION ADMIT | 留观后入院 | 84,437 |
| URGENT | 紧急入院 | 54,929 |
| SURGICAL SAME DAY ADMISSION | 日间手术 | 42,898 |
| DIRECT OBSERVATION | 直接留观 | 24,551 |
| DIRECT EMER. | 直接急诊 | 21,973 |
| ELECTIVE | 择期入院 | 13,130 |
| AMBULATORY OBSERVATION | 门诊留观 | 7,195 |

### 6.2 生命体征（#6-#14）

### 6.3 DS 章节字段（#15-#21, #33-#37）

以下字段均从选定的 DS 出院小结 `text` 中按章节标题提取。

#### DS 选择规则

每个 Visit 可能有多份 DS（note_type=DS）。选择规则：

1. 候选条件：`note_type=DS`、`hadm_id` 匹配、`subject_id` 一致、`text` 非空
2. 对每份候选 DS 独立解析 Chief Complaint 章节，只保留包含明确非空主诉的候选
3. 在有效候选中，按 `note_seq` -> `charttime` -> `storetime` -> `note_id` 降序选最新记录
4. 选中的 DS 同时作为以下全部章节字段的共同来源，不合并不同 DS 的章节

#### 章节解析规则

- 大小写不敏感的顶层标题匹配，允许标题末尾带英文冒号
- 章节内容从标题之后开始，到下一个已知顶层标题之前结束
- 去除章节首尾空白，保留内部原文、顺序、换行和 `___` 去标识化标记

#### `narrative.chief_complaint`（#15）

- **流程需求**: 本次就诊的主要症状或就诊原因，是题型①②③④的题干核心。
- **必需性**: 必需。所有候选 DS 均无明确 Chief Complaint 时排除 Visit。

#### `narrative.history_of_present_illness`（#16）

- **流程需求**: 症状的起病方式、持续时间和变化过程。
- **章节标题**: `History of Present Illness`

#### `narrative.past_medical_history`（#17）

- **流程需求**: 当前决策前已存在的疾病。
- **章节标题**: `Past Medical History`
- **有效状态**: `None`、`No past medical history` 是有效 str，不视为缺失。

#### `narrative.social_history`（#18）

- **流程需求**: 吸烟/饮酒/职业/毒品使用。
- **章节标题**: `Social History`
- **章节存在率**: 97.4%。

#### `narrative.medications_on_admission`（#19）

- **流程需求**: 入院前正在使用的药物。
- **章节标题**: `Medications on Admission`
- **章节边界**: 到下一个已知标题之前结束。
- **有效状态**: `None`、`No medications` 是有效 str。

#### `narrative.allergies`（#20）

- **流程需求**: 涉及药物时是安全必需件。
- **章节标题**: `Allergies`
- **章节存在率**: 99.9%。
- **有效状态**: `No Known Allergies / Adverse Drug Reactions` 是有效 str。

#### `narrative.physical_exam`（#21）

- **流程需求**: 体格检查发现辅助鉴别诊断和治疗决策。
- **章节标题**: `Physical Exam`

#### `narrative.discharge_note_full`（#37）

- **流程需求**: 选定 DS 的完整 `text` 原文。备用——章节解析失败时从完整原文恢复；出题时如需引用未设独立字段的章节，可直接从此字段提取。
- **信息隔离**: 不作为任何题型的题干或答案来源直接使用。

### 6.4 检查检验（#22）

#### `investigations`（#22）

- **流程需求**: 记录住院期间进行的全部检查检验。题型①的**答案来源**，题型②③④⑤的**条件题干**。抽取层忠实记录全量数据，信息隔离由出题层实现。
- **来源**: labevents + d_labitems（实验室）；poe + poe_detail（心脏/呼吸）；radiology + radiology_detail（影像）。
- **数据规模**（数据验证）：单个 Visit 平均 45 种不同检验项目、~190 条 labevents，p90 约 81 种项目。Lab 按 itemid 聚合后约 30-50KB/Visit。
- **保存格式**: JSON 对象，固定包含 `laboratory`、`radiology`、`cardiology`、`respiratory` 四个数组。

**Laboratory**（按 itemid 聚合，保留全时序）:

```json
{
  "itemid": 50912,
  "label": "Creatinine",
  "fluid": "Blood",
  "category": "Chemistry",
  "results": [
    {"charttime": "2103-01-15T08:00:00", "value": "1.5", "valuenum": 1.5, "valueuom": "mg/dL", "ref_range_lower": 0.4, "ref_range_upper": 1.1, "flag": "abnormal"},
    {"charttime": "2103-01-16T08:00:00", "value": "1.3", "valuenum": 1.3, "valueuom": "mg/dL", "ref_range_lower": 0.4, "ref_range_upper": 1.1, "flag": null}
  ]
}
```

每个 lab 元素按 itemid 聚合，`results` 数组保留该项目的全部有效测量时序（按 charttime 升序）。全时序保留的原因：文本训练和临床推理的核心价值之一是理解病情演变（如"肌酐从 1.5 降到 1.3，趋势好转"），丢弃时序等于丢弃住院期间最重要的病情动态。

有效结果定义：`value`/`valuenum`/`comments` 至少一个非空。时间相同时用 `storetime`、`labevent_id` 稳定排序。

**Radiology**（每份报告一条）:

```json
{
  "exam_name": "CT HEAD W/O CONTRAST",
  "charttime": "2103-01-15T10:30:00",
  "text": "CT head without contrast shows no acute intracranial hemorrhage...",
  "details": [{"field_name": "exam_name", "field_value": "CT HEAD W/O CONTRAST", "field_ordinal": 1}]
}
```

只使用 `note_type=RR` 的正式放射学报告。同一 exam_name 只保留 charttime 最早的报告。

**Cardiology / Respiratory**（仅有医嘱层信息）:

```json
{"order_subtype": "ECG", "ordertime": "2103-01-15T09:00:00", "poe_detail": [{"field_name": "Study", "field_value": "12 LEAD"}]}
```

来源 `poe`（`transaction_type='New'`，`order_type='Cardiology'` 或 `'Respiratory'`）+ `poe_detail`。这些检查类型在 MIMIC 中没有结构化结果表，仅保存医嘱层信息。

- **去重**: 同一 Visit 中内容相同的医嘱只保留最早的一条。
- **排序**: 最终数组按时间升序。
- **缺失表示**: `{"laboratory":[],"radiology":[],"cardiology":[],"respiratory":[]}`。

### 6.5 诊断（#23-#26）

#### `diagnoses.primary`（#23-#25）

- **流程需求**: 主诊断是题型②的**答案来源**，也是题型③④⑤的**题干信息**。
- **来源**: `diagnoses_icd`（`seq_num=1` 为主诊断）+ `d_icd_diagnoses`。
- **主诊断选择**: 当前 Visit 必须恰好存在一条 `seq_num=1` 记录，`icd_code` 非空，`icd_version` 为 9 或 10，且能连接诊断字典。不满足时排除 Visit。
- **保存格式**:
  - `diagnoses.primary.icd_code`: str，保留源格式，保留前导零
  - `diagnoses.primary.diagnosis_name`: str，`d_icd_diagnoses.long_title` 英文原名
  - `diagnoses.primary.icd_version`: str，`9->ICD-9-CM`，`10->ICD-10-CM`

#### `diagnoses.other`（#26）

- **流程需求**: 题型②的**答案来源**（鉴别诊断）和题型③④⑤的**条件题干**（共病影响治疗和随访决策）。
- **来源**: `diagnoses_icd`（`seq_num>1`）+ `d_icd_diagnoses`。
- **保存格式**: JSON 字符串数组，每个元素为 `d_icd_diagnoses.long_title` 英文名称。
- **排序**: 按 `seq_num` 升序。
- **去重**: 名称（忽略大小写、合并连续空白）相同的诊断只保留排序最前的一项；移除与 `diagnoses.primary.diagnosis_name` 相同的项目。
- **缺失表示**: `[]`。

### 6.6 药物处方与操作（#27-#28）

#### `treatments.medications`（#27）

- **流程需求**: 题型③的**答案来源**——出题问"最适当的治疗"，答案来自实际开具的药物处方。
- **来源**: `prescriptions`（`drug_type=MAIN`）。
- **保存格式**: JSON 对象数组。每个对象固定属性：

```json
{"drug": "Vancomycin", "prod_strength": "500 mg", "form_rx": "VIAL", "dose_val_rx": "1000", "dose_unit_rx": "mg", "route": "IV", "doses_per_24_hrs": 2}
```

- **全时序保留**: 保留同一药物的全部处方记录（按 `starttime` 升序），不丢弃剂量调整。与 Lab 全时序同理——住院期间的剂量变化（如万古霉素 1g q12h -> 500mg q8h）是重要的治疗决策信息，丢弃等于丢失治疗演变。
- **排序**: 按各处方的 `starttime` 升序；同一药物的多条记录保持时间顺序排列。
- **缺失表示**: `[]`。

#### `treatments.procedures`（#28）

- **流程需求**: 题型③的**答案来源**——出题问"最适当的处置"，答案可能是手术或操作。
- **来源**: `procedures_icd` + `d_icd_procedures`。
- **保存格式**: JSON 对象数组。每个对象固定属性：

```json
{"procedure_name": "Insertion of endotracheal tube", "icd_code": "9604", "icd_version": 9}
```

- **去重**: 相同 `icd_code + icd_version` 只保留 `chartdate` 最早的一条。
- **排序**: 按 `chartdate` -> `seq_num` 升序。
- **缺失表示**: `[]`。

- **流程需求**: 题型④的**答案来源**——出题问"最应转介至哪个科室"，答案来自最终负责治疗的科室。

#### `disposition.admission_location`（#30）

- **流程需求**: 患者入院前的位置，辅助判断就诊途径。题型④条件题干。

## 十、通用存储规则

- JSONL 文件使用 UTF-8 编码，换行符 `\n`。每行是一个完整的 JSON 对象（一个 visit），行间无分隔符。
- `subject_id`、`hadm_id`、`diagnoses.primary.icd_code` 按字符串处理，保留前导零。
- 标量非必需字段缺失时写 JSON `null`；集合字段无元素时写空数组 `[]`；investigations 写 `{"laboratory":[],"radiology":[],"cardiology":[],"respiratory":[]}`。
- JSON 对象的固定属性必须完整；源字段缺失时保存 JSON `null`。有效字符串保存为 JSON 字符串，有效数值保存为 JSON 数值。
- DS 章节字段（#15-#21, #33-#37）使用同一份选定 DS，不合并不同 DS 的章节内容。
- 生命体征数值字段（vitals.temperature~acuity）保存数值或 null；源值无法解析为数值时写 null。
- `vitals.rhythm` 保存文本或 null。
- `vitals.source` 当任一生命体征非空时写 `"triage"`；全部为空时写 null。
- `narrative.allergies` 中明确记录的 `No Known Allergies / Adverse Drug Reactions` 是有效 str，不视为缺失。
- 文本字段保留内部换行。
- 体积估算：~40KB/visit x ~30 万 eligible visit ~ 12GB（gzip 后约 2.5GB）。
