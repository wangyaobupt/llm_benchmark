# 出题数据抽取规范

> **生成日期**: 2026-08-07
> **数据版本**: MIMIC-IV v3.1 (hosp/icu) + MIMIC-IV-ED v2.2 (ed) + MIMIC-IV-Note v2.2 (note)
> **配套文档**: `data/出题数据抽取字段规范.md`（38 字段定义与流程推导）

---

## 一、文档定位

本文档定义从 MIMIC-IV 原始表抽取 38 字段 visit 级 CSV 的**操作规范**：管线架构、表关联、逐阶段规则、纳入条件和质量验证。字段定义见配套文档，本文不重复字段语义，只规定怎么取。

## 三、抽取管线架构

### 3.1 管线总览

```text
Stage 0  加载 admissions → 候选 Visit 集合
Stage 1  关联 patients → 人口统计筛选（年龄≥18、性别有效）
Stage 2  关联 diagnoses_icd + d_icd_diagnoses → 诊断筛选（有效主诊断）
Stage 3  关联 discharge(DS) → 出院小结筛选（有效 DS + Chief Complaint）
         ──── 纳入漏斗结束，得到 eligible Visit 集合 ────
Stage 4  提取 DS 章节字段（11 个 DS 章节字段 + 全文）
Stage 5  提取结构化临床字段（orders/labs/radiology/prescriptions/procedures）
Stage 6  提取新增字段（admission_type/admission_location/discharge_location/
         services/ed_disposition/vital_signs 组）
Stage 7  组装 + 验证 + 写入
```

### 3.2 漏斗模型

```
admissions 全部住院          N₀
  - 无有效 patients 关联
  - 年龄 < 18 或无法计算
  - 性别无效
                              ↓ Stage 1
人口统计通过                  N₁
  - 无有效 seq_num=1 主诊断
  - 主诊断无法连接字典
                              ↓ Stage 2
诊断通过                      N₂
  - 无 note_type=DS 的出院小结
  - DS 无明确 Chief Complaint
                              ↓ Stage 3
eligible Visit                N₃
```

**Stage 3 之后不再排除 Visit**。对 eligible Visit 中的非必需字段，缺失按规则表示，不影响 Visit 纳入。

### 3.3 处理顺序

- Stage 0-3 顺序执行，每个 Stage 的输出约束下一个 Stage 的输入范围。
- Stage 4-6 可以并行（均只处理 eligible Visit 的 `hadm_id`），但同一 `hadm_id` 的各阶段结果在 Stage 7 汇合。
- 所有源表按 `hadm_id` 过滤后再处理；`hadm_id` 为空或不在 admissions 中的记录直接忽略。

## 四、Visit 定义与纳入条件

### 4.1 Visit 定义

- 一个 Visit 等于一个 `hadm_id`，是行的唯一主键。
- `hadm_id` 来自 `admissions.csv`，不得从其他表推导或改写。
- 每个 `hadm_id` 在 admissions 中唯一非空；重复或缺失视为全局错误，终止抽取。
- 同一 `subject_id` 可对应多个 `hadm_id`；各 Visit 独立处理，不跨住院合并。

### 4.2 Stage 0: 候选 Visit

- 从 `admissions.csv` 读取全部行。
- `subject_id` 和 `hadm_id` 去首尾空白，空值视为全局错误。
- `hadm_id` 重复视为全局错误。
- 保留 admissions 源文件顺序作为候选顺序。
- 可选 `--limit N` 截取前 N 个候选。

### 4.3 Stage 1: 人口统计筛选

**关联**: `admissions.subject_id` → `patients.subject_id`（必须 1:1）。

**计算**:

```text
age_at_encounter = anchor_age + year(admittime) - anchor_year
```

**排除条件**（任一满足即排除）:
- `patients` 关联缺失、重复或 `subject_id` 冲突
- `anchor_age`、`anchor_year` 或 `admittime` 无效
- `age_at_encounter` < 18
- `gender` 不是 `M` 或 `F`

**同时提取的字段**: `age_at_encounter`(#3)、`sex`(#4)。

### 4.4 Stage 2: 诊断筛选

**关联**: `admissions.hadm_id` → `diagnoses_icd.hadm_id`。

**主诊断有效条件**:
- 当前 Visit 恰好存在一条 `seq_num=1` 记录
- `icd_code` 去首尾空白后非空
- `icd_version` 为 9 或 10
- `icd_code + icd_version` 能精确连接 `d_icd_diagnoses` 到唯一非空 `long_title`

**排除条件**: 无有效主诊断、有多条 `seq_num=1` 记录、或主诊断无法连接字典。

**同时提取的字段**: `primary_icd_code`(#24)、`primary_diagnosis_name`(#25)、`primary_icd_version`(#26)、`other_diagnoses`(#27)。

### 4.5 Stage 3: 出院小结筛选

**关联**: `admissions.hadm_id` → `discharge.hadm_id`（`note_type=DS`）。

**DS 候选条件**:
- `note_type = DS`（`AD` 补充记录不纳入）
- `hadm_id` 等于当前 Visit
- `subject_id` 与 admissions 一致
- `text` 非空

**DS 选择规则**: 对每份候选 DS 独立解析 Chief Complaint 章节。只保留包含明确非空主诉的候选。在有效候选中按以下优先级降序选最新:

1. `note_seq`（越大越新）
2. `charttime`（越大越新）
3. `storetime`（越大越新；空值排在非空之后）
4. `note_id`（字符串降序）

**排除条件**: 无符合条件的 DS，或所有候选 DS 均无明确非空 Chief Complaint。

## 五、逐阶段提取规则

### 5.1 Stage 4: DS 章节字段

选定的 DS 同时作为以下 12 个字段的共同来源，不合并不同 DS 的章节:

`chief_complaint`(#15)、`history_of_present_illness`(#16)、`past_medical_history`(#17)、`social_history`(#18)、`medications_on_admission`(#19)、`allergies`(#20)、`physical_exam`(#21)、`brief_hospital_course`(#34)、`discharge_medications`(#35)、`discharge_condition`(#36)、`discharge_record`(#37)、`discharge_note_full`(#38)。

#### 已知顶层标题列表

```text
Chief Complaint
History of Present Illness
Past Medical History
Social History
Family History
Allergies
Physical Exam
Pertinent Results
Studies
Brief Hospital Course
Medications on Admission
Discharge Medications
Discharge Diagnosis
Discharge Condition
Discharge Instructions
Follow-up Instructions
Followup Instructions
Follow Up Instructions
```

#### 章节解析算法

1. 将 `text` 中的 `\r\n` 和 `\r` 统一为 `\n`
2. 用正则匹配顶层标题行：行首可选空白 + 标题文本（忽略大小写）+ 可选冒号 + 行尾
3. 对每个目标章节，内容从标题行之后开始，到下一个已知顶层标题行之前结束
4. 去除章节内容首尾空白
5. 章节内容为空时，对应字段写空单元格（chief_complaint 为空时排除 Visit）

#### 逐章节字段

| # | 字段 | 匹配标题 | 章节别名 |
|--:|---|---|---|
| 15 | chief_complaint | Chief Complaint | |
| 16 | history_of_present_illness | History of Present Illness | |
| 17 | past_medical_history | Past Medical History | |
| 18 | social_history | Social History | |
| 19 | medications_on_admission | Medications on Admission | |
| 20 | allergies | Allergies | |

| 35 | discharge_medications | Discharge Medications | |
| 36 | discharge_condition | Discharge Condition | |
| 37 | discharge_record | Discharge Instructions | |

**discharge_record(#37) 特殊规则**: 匹配 `Discharge Instructions`（不是 Follow-up Instructions）。原因见字段规范 §3.7 和 §5.4 数据验证记录。

**follow-up instructions 不可用性检测**: 抽取时对选定 DS 检测 Follow-up Instructions 章节内容。如果去除空白后内容仅为 `___` 模式，记录警告日志（不阻断抽取），确认该字段确实不可用。

### 5.2 Stage 5: 结构化临床字段

#### investigation_orders（#22）

**来源**: `poe.csv` + `poe_detail.csv`。

**过滤**:
- `hadm_id` 等于当前 Visit，`subject_id` 一致
- `transaction_type = New`
- `order_type IN ('Lab', 'Radiology', 'Cardiology', 'Respiratory')`

**明细关联**: `poe_detail` 通过 `poe_id + poe_seq` 连接 `poe`。明细按 `field_name` 稳定排序，`field_name` 相同时保留源文件行序。

**去重**: `order_type + order_subtype + 排序后 poe_detail 内容` 相同的医嘱只保留 `ordertime` 最早的一条。

**排序**: 最终数组按 `ordertime → poe_id → poe_seq → 源文件行序` 升序。

**输出**: JSON 对象数组，每个对象固定属性 `{order_type, order_subtype, poe_detail}`。

#### investigation_reports（#23）

**实验室部分**（来源: `labevents` + `d_labitems`）:
- 关联: `hadm_id` 匹配，`labevents.itemid` → `d_labitems.itemid`
- 有效结果: `value`、`valuenum` 或 `comments` 至少一个非空
- 项目选择: 同一 `itemid` 只保留 `charttime` 最早的有效结果；时间相同时用 `storetime`、`labevent_id` 稳定选择
- 保存: `{d_labitems: {itemid, label, fluid, category}, labevents: {value, valuenum, valueuom, ref_range_lower, ref_range_upper, flag, comments}}`

**影像部分**（来源: `radiology` + `radiology_detail`）:
- 关联: `hadm_id` 匹配，`radiology.note_id` → `radiology_detail.note_id`
- 正式报告: 只使用 `note_type = RR`
- 项目识别: `radiology_detail` 中 `field_name = exam_name` 对应的 `field_value`
- 项目选择: 同一 `exam_name` 只保留 `charttime` 最早的报告
- 保存: `{radiology: {text}, radiology_detail: [{field_name, field_value, field_ordinal}]}`

**输出**: JSON 对象 `{laboratory: [...], radiology: [...]}`。

#### medication_prescriptions（#28）

**来源**: `prescriptions.csv`。

**过滤**: `drug_type = MAIN`（排除 BASE 和 ADDITIVE），`drug` 去首尾空白后非空。

**去重**: 同一药物（`drug` 忽略大小写、合并空白）只保留 `starttime` 最早的记录。

**排序**: 按各药物首次处方 `starttime` 升序。

**输出**: JSON 对象数组，固定属性 `{drug, prod_strength, form_rx, dose_val_rx, dose_unit_rx, route, doses_per_24_hrs}`。

#### procedures（#29）

**来源**: `procedures_icd.csv` + `d_icd_procedures.csv`。

**过滤**: `icd_code` 非空，`icd_version` 为 9 或 10，能连接到非空 `long_title`。

**去重**: 相同 `icd_code + icd_version` 只保留 `chartdate` 最早的一条。

**排序**: 按 `chartdate → seq_num → icd_version → icd_code` 升序。

**输出**: JSON 对象数组，固定属性 `{procedure_name, icd_code, icd_version}`。

### 5.3 Stage 6: 新增来源字段

#### admissions 直接字段（#5, #31, #32）

这三个字段直接从 `admissions.csv` 中与 `hadm_id` 同行读取:

| # | 字段 | admissions 列 | 必需性 |
|--:|---|---|---|
| 5 | admission_type | `admission_type` | 必需（空则排除 Visit） |
| 31 | admission_location | `admission_location` | 非必需 |
| 32 | discharge_location | `discharge_location` | 非必需 |

**实现**: 在 Stage 0 加载 admissions 时即可读取这些列，无需额外源表扫描。

#### primary_service（#30）

**来源**: `services.csv`。

**关联**: `hadm_id` 匹配，`subject_id` 一致。

**选择**: 按 `transfertime` 升序取最后一条记录的 `curr_service`。

**缺失**: 无 services 记录时写空单元格。

#### ed_disposition（#33）

**来源**: `edstays.csv`。

**关联**: `edstays.hadm_id` 等于当前 Visit。一次住院在 edstays 中最多一条匹配记录。

**选择**: 取 `disposition` 列值。如多条记录（罕见），取 `intime` 最晚的一条。

**缺失**: 无 ED 关联时写空单元格。

#### 生命体征组（#6-#14）

**关联链**:

```text
admissions.hadm_id → edstays.hadm_id → edstays.stay_id
edstays.stay_id → triage.stay_id     (temperature~acuity)
edstays.stay_id → vitalsign.stay_id  (rhythm)
```

**triage 提取**（#6-#12）:

| # | 字段 | triage 列 | 解析 |
|--:|---|---|---|
| 6 | temperature | temperature | float，无法解析时空 |
| 7 | heartrate | heartrate | float |
| 8 | resprate | resprate | float |
| 9 | o2sat | o2sat | float |
| 10 | sbp | sbp | float |
| 11 | dbp | dbp | float |
| 12 | acuity | acuity | int |

**rhythm 提取**（#13）: 从 `vitalsign` 表按 `stay_id` 关联，取首次非空 `rhythm` 值。

**vital_source**（#14）: 当 #6-#13 任一非空时写 `triage`；全部为空时写空字符串。

**覆盖率**: 46.8% 的 eligible Visit 有 triage 数据。无 triage 时 #6-#13 写空单元格，#14 写空字符串。

## 六、输出格式

### 6.1 文件与粒度

- 唯一输出文件为 `rwd_benchmark_visits.csv`。
- 每个 eligible `hadm_id` 恰好一行，`hadm_id` 在文件内唯一。
- 输出保留 admissions 源文件顺序（候选顺序）。
- CSV 表头固定为 38 列，列顺序见字段规范 §4.1。

### 6.2 通用存储规则

- UTF-8 编码，换行符 `\n`。
- `subject_id`、`hadm_id`、`primary_icd_code` 按字符串处理，保留前导零。
- 标量非必需字段缺失时写空单元格。
- 集合字段无元素时写合法 JSON：数组字段写 `[]`，investigation_reports 写 `{"laboratory":[],"radiology":[]}`。
- 不使用 `nan`、`None`、`null` 字符串表示缺失。
- JSON 对象的固定属性必须完整；源值缺失时保存 JSON `null`，有效字符串保存为 JSON 字符串，有效数值保存为 JSON 数值。
- 含逗号、双引号或换行的文本按标准 CSV 规则引用和转义。文本字段保留内部换行。
- 生命体征独立列（#6-#12）保存数值或空单元格。
- `allergies`(#20) 中 `No Known Allergies / Adverse Drug Reactions` 是有效 str，不视为缺失。

## 七、质量验证

## 八、错误处理

### 8.1 全局终止条件

以下错误终止整个抽取，不跳过、不兜底:

| 错误类型 | 条件 | 原因 |
|---|---|---|
| 基础 ID 错误 | admissions 中 subject_id 或 hadm_id 为空 | 数据完整性破坏 |
| hadm_id 重复 | admissions 中同一 hadm_id 出现多次 | 违反唯一性 |
| subject 关联冲突 | 任何源表中 subject_id 与 admissions 不一致 | 数据完整性破坏 |
| 源文件缺失 | 16 张必需表中任一不存在 | 环境配置错误 |

### 8.2 Visit 排除条件

以下情况排除单个 Visit，不影响其他 Visit:

| 排除阶段 | 条件 |
|---|---|
| Stage 1 | 无有效 patients 关联；年龄 < 18 或无法计算；性别无效 |
| Stage 2 | 无有效 seq_num=1 主诊断；多条 seq_num=1；主诊断无法连接字典 |
| Stage 3 | 无符合条件的 DS；所有候选 DS 无明确 Chief Complaint |

### 8.3 字段级缺失处理

非必需字段缺失时按统一规则表示缺失，不影响 Visit 纳入:
- 标量字段写空单元格
- JSON 数组字段写 `[]`
- investigation_reports 写 `{"laboratory":[],"radiology":[]}`

### 8.4 禁止操作

以下操作在任何阶段均禁止:
- 从其他 Visit、同一患者的其他住院或 LLM 推断补全字段值
- 跨 DS 合并章节内容
- 将 ICD-9 转换为 ICD-10 或反向
- 将 `note_type=AD` 补充记录纳入 DS 候选集
- 从 follow-up instructions（已不可用）提取离院指导内容
- 根据 age_at_encounter 计算"年龄段"并替代原始年龄
- 标准化、翻译或改写任何源文本值

## 九、与现有实现的差异

现有 `rwd_pipeline/extraction/` 代码实现 17 字段的抽取管线。本规范定义的 38 字段管线需要在现有基础上新增以下能力:

### 9.1 需新增的管线阶段

| 阶段 | 现有实现 | 需新增 |
|---|---|---|
| Stage 0 | 加载 admissions（仅 subject_id, hadm_id, admittime） | 同时读取 admission_type, admission_location, discharge_location |
| Stage 4 | 解析 5 个 DS 章节 | 扩展为解析 11 个 DS 章节 + 保存全文 |
| Stage 6 | 不存在 | 新增: services 提取、ED 关联与 triage/vitalsign 提取、ed_disposition 提取 |

### 9.2 需新增的数据源

| 表 | 现有实现 | 需新增 |
|---|---|---|
| admissions | 仅 3 列 | 增读 4 列（admission_type, admission_location, discharge_location） |
| services | 未使用 | 新增 |
| edstays | 未使用 | 新增 |
| triage | 未使用 | 新增 |
| vitalsign | 未使用 | 新增 |

### 9.3 需修正的规则

| 规则 | 现有实现 | 修正 |
|---|---|---|
| investigation_orders 过滤 | order_type IN (Lab, Imaging) | order_type IN (Lab, Radiology, Cardiology, Respiratory) |
| discharge_record 来源 | Follow-up Instructions | Discharge Instructions |

### 9.4 输出 schema 变更

现有 `OUTPUT_COLUMNS` 为 17 列。需扩展为 38 列，列顺序见字段规范 §4.1。`build_output_frame` 和 `validate_output` 需相应更新。
